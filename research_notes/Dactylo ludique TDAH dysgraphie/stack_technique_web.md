## 1. Gestion du clavier sur le web (point critique)

### Takeaway
Il n'existe aucun moyen fiable et universel de connaître la disposition active : `navigator.keyboard.getLayoutMap()` n'existe que dans Chromium (ni Firefox ni Safari), ne renvoie que la couche sans modificateur et pas forcément la disposition active. Il faut donc (a) valider la frappe sur le **caractère produit** (`key` / `beforeinput`/`input` + événements de composition), (b) utiliser `code` uniquement pour la position physique (clavier virtuel à l'écran, doigté, inférence de disposition), et (c) faire **choisir/confirmer** la disposition par l'utilisateur, à partir d'un catalogue de dispositions décrites en données.

### Cited Findings

**`key` / `code` / `keyCode`**
- `KeyboardEvent.code` « represents a physical key on the keyboard (as opposed to the character generated by pressing the key) » ; la valeur « isn't altered by keyboard layout or the state of the modifier keys ». Exemple MDN : `code === "KeyQ"` correspond à la touche Q en QWERTY, à `'` en Dvorak et à **A en AZERTY**. MDN avertit qu'on ne peut pas déduire de `code` le caractère produit ni le nom de la touche pour l'utilisateur — [MDN KeyboardEvent.code](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/code)
- `KeyboardEvent.key` renvoie le caractère imprimable (avec prise en compte de Maj), une valeur nommée pour les touches spéciales, **`"Dead"` pour l'appui sur une touche morte**, et `"Unidentified"` si la touche ne peut être identifiée. Séquence nominale : `keydown` → (`beforeinput` → `input` si un caractère est inséré dans un champ éditable) → `keyup` — [MDN KeyboardEvent.key](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/key)
- La spec UI Events (W3C **Working Draft du 21 février 2026**, toujours pas Candidate Recommendation) ne définit pas de valeurs pour `keyCode`/`charCode`, note qu'ils sont « inconsistent across platforms » et recommande `key` et `code` ; `which` est classé historique. `keydown` DOIT précéder `beforeinput`, `input` et `keyup` pour une même touche ; `isComposing` vaut `true` « during a dead key sequence or while an input method editor is active » — [W3C UI Events](https://www.w3.org/TR/uievents/)

**Touches mortes et composition**
- Fil W3C (2016, R. Niwa pour Apple/Google/Microsoft) : tous les navigateurs déclenchent des événements de composition pour les touches mortes **sur macOS mais pas sur Windows** ; sur Windows la touche morte n'insère rien et la seconde touche insère le caractère composé ; sous Linux, l'appui sur la touche morte n'insérait ni caractère ni événement de composition — [W3C public-webapps 2016](https://lists.w3.org/Archives/Public/public-webapps/2016JanMar/0033.html)
- Issue UI Events (2023) : pendant une composition, la valeur de `key` diverge — Firefox envoie tantôt le symbole non composé, tantôt le composé ; Chrome le symbole non composé ou `"Process"` ; WebKit le symbole non composé ou `"Unidentified"`. Sous Linux, les trois moteurs envoyaient U+00A8 dans `compositionupdate.data` au lieu de U+0308 — [W3C uievents issue (2023)](https://lists.w3.org/Archives/Public/public-webapps-github/2023Jun/0593.html)
- Safari : ordre observé `compositionstart, compositionupdate, input, keydown, keyup` (non conforme) ; la touche qui valide une composition arrive avec `isComposing === false` car `keydown` est envoyé après `compositionend` ; le rapporteur recommande de tester aussi `keyCode === 229` — [WebKit bug 165004](https://bugs.webkit.org/show_bug.cgi?id=165004)
- MDN confirme : `compositionstart` peut arriver après `keydown` et `compositionend` avant `keydown` ; dans ces cas `isComposing` est faux mais `keyCode` vaut 229 ; garde recommandée : `if (event.isComposing || event.keyCode === 229) return;`. Depuis Firefox 65, `keydown`/`keyup` sont émis pendant la composition IME — [MDN keydown event](https://developer.mozilla.org/en-US/docs/Web/API/Element/keydown_event)

**AltGr**
- Sous Windows, l'appui sur AltGr génère **deux** événements (`ControlLeft` puis `AltRight`) dans Firefox, Chrome et Edge ; sous Linux et Mac, un seul `AltRight` — [copy/v86 issue 1127](https://github.com/copy/v86/issues/1127)
- `getModifierState("AltGraph")` dans Firefox : vrai sous Windows si Alt+Ctrl ou AltGr ; sous Linux (GTK) si Level 3/Level 5 Shift ; sous macOS si ⌥ Option — [MDN getModifierState](https://developer.mozilla.org/en-US/docs/Web/API/KeyboardEvent/getModifierState)
- Gecko : quand AltGr produit un caractère, `altKey` et `ctrlKey` sont rapportés faux ; Chromium ne positionne l'état AltGraph que si la disposition active possède AltGr ou si un caractère est saisi via Ctrl+Alt — [Mozilla bug 900750](https://bugzilla.mozilla.org/show_bug.cgi?id=900750)
- Bug ouvert (octobre 2026) dans TanStack Hotkeys : Chrome/Windows rapporte Ctrl+Alt + AltGraph pour AltGr+touche, et un code qui ne teste que les modificateurs prend des caractères AltGr (µ, ć) pour des frappes sans modificateur — [TanStack/hotkeys #169](https://github.com/TanStack/hotkeys/issues/169)

**Keyboard API (`getLayoutMap`)**
- Support : Chrome 69+, Edge 79+, Opera 56+, Chrome Android 69+ ; **Firefox : non ; Safari (macOS/iOS) : non** ; API expérimentale, contexte sécurisé requis — [données de compatibilité MDN (miroir w3cub)](https://docs.w3cub.com/dom/keyboard/getlayoutmap), [MDN Keyboard API](https://developer.mozilla.org/en-US/docs/Web/API/Keyboard_API)
- Spécification : *Draft Community Group Report* du 17 juin 2022 (pas un standard). La carte ne couvre que les « writing system keys », **sans modificateur** ; elle provient de la disposition **ASCII-capable de plus haute priorité** (pas nécessairement la disposition active) ; une touche morte y est remplacée par un caractère autonome (`` ` `` `'` `^` `~` `¨`) ; les plateformes mobiles peuvent renvoyer une carte partielle ou vide ; l'empreinte numérique (fingerprinting) est reconnue comme risque ; politique de permissions `keyboard-map` ; événement `layoutchange` spécifié — [WICG Keyboard Map](https://wicg.github.io/keyboard-map/)

**Mobile / tablettes / claviers virtuels**
- `KeyboardEvent.code` est implémenté sur iOS depuis 2017 (r210668) — [WebKit bug 166932](https://bugs.webkit.org/show_bug.cgi?id=166932)
- Sur Android avec clavier **virtuel**, `key` vaut `"Unidentified"` et `keyCode` 229 pour presque toutes les touches ; `preventDefault()` sur `keydown` est sans effet ; un ingénieur Chromium l'explique et recommande `beforeinput`/`input` — [W3C public-editing-tf 2017](https://lists.w3.org/Archives/Public/public-editing-tf/2017Jun/0005.html)

**Sources de données libres pour décrire les dispositions**
- **Unicode CLDR keyboards 3.0** : le dossier `keyboards/3.0` ne contient que **13 fichiers** (dont `fr.xml`, `fr-t-k0-test.xml`, `pt-t-k0-abnt2.xml`, `mt.xml`, `ja-Latn.xml`…) : pas de QWERTY US/UK, QWERTZ, AZERTY BE, BÉPO ni CSA — [unicode-org/cldr keyboards/3.0](https://github.com/unicode-org/cldr/tree/main/keyboards/3.0)
- Le `fr.xml` de CLDR est la disposition **« Français normalisé (AZERTY) »** (AFNOR), schéma `keyboard3` conforme CLDR 45, avec touches mortes déclarées comme marqueurs (`\m{acute}`, `\m{caret}`, `\m{umlaut}`…) — [cldr/keyboards/3.0/fr.xml](https://raw.githubusercontent.com/unicode-org/cldr/main/keyboards/3.0/fr.xml)
- Licence des données CLDR : **Unicode License v3 (SPDX `Unicode-3.0`)**, permissive, exige de conserver la notice de copyright ; le texte de la norme LDML (UTS #35) a une notice plus restrictive — [cldr/LICENSE](https://raw.githubusercontent.com/unicode-org/cldr/main/LICENSE). La FSF la classe « lax, permissive », compatible toutes versions de la GPL — [FSF license list](https://www.gnu.org/licenses/license-list.en.html)
- Norme AFNOR : conserve l'AZERTY et ajoute l'accès aux caractères spéciaux du français — [AFNOR](https://www.afnor.org/en/news/keyboards-3-0-a-standard-for-better-spelling-language-2) ; la disposition a été intégrée à xkeyboard-config — [xkeyboard-config MR !1](https://gitlab.freedesktop.org/xkeyboard-config/xkeyboard-config/-/merge_requests/1)
- **Kalamine** (OneDeadKey) : « text-based, cross-platform Keyboard Layout Maker » ; entrée TOML (couches `base`, `--altgr`, touche morte `--1dk`, géométrie ANSI/ISO/ERGO, dessinées en ASCII-art dans le TOML) ; sorties `.klc`, `.ahk`, `.keylayout`, `.xkb_*`, **`layout.json` (web)** et `.svg` ; licence **MIT** ; dernier push juin 2026 — [README kalamine](https://raw.githubusercontent.com/OneDeadKey/kalamine/main/README.rst), [LICENSE](https://raw.githubusercontent.com/OneDeadKey/kalamine/main/LICENSE), [exemple ansi.toml](https://raw.githubusercontent.com/OneDeadKey/kalamine/main/layouts/ansi.toml), [dépôt](https://github.com/OneDeadKey/kalamine)
- **x-keyboard** (OneDeadKey) : web component sans dépendance pour afficher/émuler des dispositions, basé sur `KeyboardEvent.code` ; JSON décrivant couches base et AltGr/Option, touches mortes et géométrie ; licence **MIT** — [OneDeadKey/x-keyboard](https://github.com/OneDeadKey/x-keyboard)
- **Ergo-L** : disposition optimisée français+anglais, une touche morte pour les accents fréquents, couche AltGr pour les symboles ; licence **WTFPL v2** — [README](https://raw.githubusercontent.com/Nuclear-Squid/ergol/master/README.md), [LICENSE](https://raw.githubusercontent.com/Nuclear-Squid/ergol/master/LICENSE)
- **kbdlayout.info** : référence des dispositions Windows regroupées par langue (inférées des KLID) ; **aucune licence ni copyright indiqué** sur la page « about » — [kbdlayout.info/about](https://kbdlayout.info/about)
- **Monkeytype** : dispositions en JSON (`frontend/static/layouts/*.json`) sous forme `{"type":"iso","keys":{"row1":[["&","1"],["é","2","~"],…]}}` (tableau de caractères par niveau, rangée par rangée, sans `code`, sans doigté, sans notion explicite de touche morte) ; dépôt sous **GPL-3.0** — [azerty.json](https://raw.githubusercontent.com/monkeytypegame/monkeytype/master/frontend/static/layouts/azerty.json), [LICENSE](https://raw.githubusercontent.com/monkeytypegame/monkeytype/master/LICENSE)

**Tests**
- Playwright : « For characters that are not on a US keyboard, only an input event will be sent » ; `keyboard.insertText` « Dispatches only input event, does not emit the keydown, keyup or keypress events » ; la doc ne traite ni touches mortes ni composition — [Playwright Keyboard](https://playwright.dev/docs/api/class-keyboard)

### Inferences
- **Architecture recommandée du moteur de frappe (inférence)** : normaliser tout événement en un objet `Frappe { code, key, mods:{shift,altGraph,ctrl,meta}, isComposing, inputType, data, t }` puis traiter dans une fonction pure `(état, frappe) → (état, résultat)`. Sources d'événements : `keydown`/`keyup` sur `window` (temps, position physique, modificateurs) **et** un `<input>`/`<textarea>` caché focalisé recevant `beforeinput`/`input`/`composition*` (texte réellement produit, indispensable pour touches mortes macOS, claviers virtuels Android et IME). Règle : la justesse se juge sur le caractère (NFC), jamais sur `code`.
- **Touches mortes** : traiter `key === "Dead"` comme « frappe intermédiaire attendue » (ni erreur ni succès) ; accepter indifféremment le chemin Windows (Dead puis caractère composé dans `key`) et le chemin macOS (composition) ; prévoir le cas « touche morte + espace » → caractère autonome. Ne pas compter d'erreur sur `ControlLeft` fantôme précédant `AltRight` sous Windows.
- **AltGr** : utiliser `getModifierState("AltGraph")` et, à défaut, considérer `ctrlKey && altKey` + `key.length === 1` comme AltGr sous Windows.
- **Détection de disposition** en trois étages : (1) Chromium : `getLayoutMap()` puis appariement avec le catalogue (attention : couche de base seulement → AZERTY FR, BE et AFNOR se distinguent par la rangée des chiffres et la ponctuation, pas par les lettres ; la carte peut refléter une autre disposition que l'active) ; (2) partout : **étalonnage interactif** (« appuie sur la touche à droite de Tab », etc.) en comparant `code` et `key` de 2-4 touches discriminantes, puis inférence passive continue ; (3) toujours un sélecteur manuel visuel, mémorisé par profil. La plateforme (Mac vs PC) se déduit du user-agent et doit pouvoir être corrigée à la main.
- **Modèle de données proposé (inférence)**, séparant trois fichiers : *géométrie* (ISO-105, ANSI-104, Apple ISO, ortholinéaire : liste des `code`, rangée, colonne, largeur, **doigt par défaut** — le doigté dépend de la position physique, pas de la disposition) ; *disposition* (`id`, noms localisés, `locale`, `plateformes`, `geometrie`, `source`+`licence`, `touches: { "KeyQ": { "base":"a", "shift":"A", "altgr":null, "shift+altgr":null }, "BracketLeft": { "base":{"morte":"circonflexe"}, "shift":{"morte":"trema"} } }`, `touchesMortes: { "circonflexe": { "seul":"^", "table":{"a":"â","e":"ê"," ":"^"} } }`) ; *index inverse généré au build* (`caractère → [séquences de frappes]`, ex. `ê → [BracketLeft, KeyE]`) servant au moteur, au clavier affiché et au calcul du doigt attendu. Format proche du JSON de Kalamine/x-keyboard, enrichi du doigté et des niveaux Shift+AltGr.
- **Chaîne d'approvisionnement des dispositions** : écrire ou importer les dispositions en TOML Kalamine (MIT ; BÉPO, Ergo-L, AZERTY, QWERTY existent déjà dans cet écosystème) et générer le JSON du projet ; compléter avec CLDR (`fr.xml` AFNOR, Unicode-3.0) et XKB. Éviter kbdlayout.info comme source de copie (licence non précisée) : s'en servir comme référence de vérification seulement. Ne pas copier les JSON de Monkeytype sauf à adopter une licence compatible GPL-3.0.
- **Tests** : Playwright ne sait pas simuler une disposition non-US ni une touche morte → tester le moteur par **rejeu de traces d'événements réelles** enregistrées sur chaque couple OS/navigateur/disposition (fixtures JSON), plus tests de propriétés ; les E2E Playwright ne couvrent que le chemin « US + insertText ».

### Gaps
- Aucune source récente (2025-2026) ne compare touche par touche le comportement des touches mortes sur Chrome/Firefox/Safari × Windows/macOS/Linux/ChromeOS : les sources trouvées datent de 2016-2023. **Une campagne de tests manuels sur matériel réel est indispensable** (enregistreur d'événements intégré à l'application).
- Non sourcé : particularités des claviers Apple AZERTY (positions de `@`, `#`, `§`, `-`, touche ⌥ comme couche 3 et touches mortes Option), comportement de Verr. Maj pour les majuscules accentuées selon OS, différences AZERTY BE, QWERTZ CH, CSA.
- Non sourcé : comportement des claviers **physiques** sur iPadOS, Android et ChromeOS (valeurs de `code`/`key`, touches mortes, choix de disposition matérielle dans les réglages). Les sources trouvées concernent les claviers virtuels.
- Licence exacte de xkeyboard-config et contenu du JSON produit par Kalamine (schéma précis) non vérifiés.
- Disponibilité de BÉPO dans CLDR 3.0 : absent du dossier consulté ; à chercher dans XKB/Kalamine.

## 2. Moteur de rendu / jeu 2D

### Takeaway
Pour des mini-jeux centrés sur du texte net, accessibles et traduisibles, l'option la plus adaptée est **hybride à dominante DOM** : interface et scènes de jeu en DOM/SVG + CSS/Web Animations (texte natif, polices système/dys, lecteurs d'écran, i18n gratuits), avec un `<canvas>` (Canvas 2D natif, ou PixiJS v8 si besoin de nombreux sprites/particules) réservé aux effets. Les moteurs complets (Phaser 4, melonJS, Godot) pèsent de 230 à 570 kB gzip, rendent le texte dans le canvas et imposent leur propre gestion d'entrées, ce qui complique précisément le point critique du projet (clavier/composition).

### Inferences
- **Critère décisif = texte et clavier.** Un moteur canvas dessine le texte en bitmap (flou possible selon `devicePixelRatio`, pas de sélection, pas de lecteur d'écran sans calque DOM parallèle, polices adaptées « dys » et réglages d'interlettrage à réimplémenter) et capte les touches via sa propre abstraction, généralement fondée sur `keyCode`/`code`, inadaptée aux touches mortes. Le DOM donne tout cela nativement et se teste avec Testing Library/axe.
- Des mini-jeux de frappe (lettres qui tombent, course, ballons, labyrinthe) mettent en scène quelques dizaines d'éléments : CSS transforms/Web Animations API + SVG suffisent largement à 60 i/s ; un `<canvas>` 2D natif en arrière-plan gère particules et décors. PixiJS n'est justifié que si un jeu dépasse quelques centaines de sprites animés.
- Adéquation au développement par IA : DOM/CSS/SVG, Canvas 2D, Phaser 3 et PixiJS sont massivement représentés dans les données d'entraînement ; **Phaser 4 (avril 2026) et KAPLAY 4000 (alpha) sont trop récents** pour être bien connus des modèles (risque de code « Phaser 3 » halluciné). PixiJS compense par un `llms.txt` et des skills officiels.
- Godot/Defold : exclus (poids du runtime WASM, texte et accessibilité hors DOM, clavier international non documenté, boucle de test navigateur plus lourde pour des agents IA).
- Architecture conseillée : un contrat `MiniJeu { monter(conteneur, contexte), demonter() }` où `contexte` expose le moteur de frappe, les tokens de thème, l'audio et l'i18n ; chaque mini-jeu choisit DOM, SVG ou canvas. Le moteur de frappe reste indépendant du rendu (testable sans navigateur).

### Gaps
- Pas de taille « tree-shakée » mesurée pour PixiJS v8 ou Phaser 4 dans un vrai build (les chiffres ci-dessus sont des bundles complets).
- Pas de source comparant la netteté du texte canvas vs DOM sur écrans HiDPI ni la qualité de `HTMLText` dans Safari.
- Qualité de la documentation/typage TypeScript de chaque moteur non évaluée de façon sourcée ; popularité relative (npm trends) non relevée.

## 3. Framework UI et outil de build

### Takeaway
**Svelte 5 + SvelteKit (adapter-static) + Vite 8 + TypeScript 6.0 + Node 24 LTS** est la combinaison cohérente au 11 octobre 2026. Attention à trois pièges d'actualité : SvelteKit 3.0 n'a que dix jours (3.0.0 le 1er octobre 2026) et une partie de l'écosystème ne le supporte pas encore ; TypeScript 7 (natif Go) est stable mais **exclu** par SvelteKit 3, svelte-check et typescript-eslint ; Node 26 ne devient LTS que fin octobre 2026.

## 4. Design tokens et thèmes sans valeurs en dur

### Takeaway
Source de vérité unique en **JSON au format DTCG 2025.10** (première version stable), transformée par **Style Dictionary 5** en (a) CSS custom properties et (b) module TypeScript typé ; le canvas lit soit le module TS, soit les variables CSS résolues via `getComputedStyle`. Les thèmes (clair/sombre/contraste élevé/dys) sont des surcharges de variables sur `[data-theme]`. L'interdiction des valeurs en dur est outillée par Stylelint + `stylelint-declaration-strict-value`.

### Cited Findings
- Le Design Tokens Community Group a publié le **28 octobre 2025** la première version stable de la spécification (2025.10) : thèmes et multi-marques, espaces colorimétriques CSS Color 4 (Display P3, Oklch…), alias et héritage. C'est un *Final Community Group Report*, **pas un standard W3C** ni sur la voie de recommandation — [annonce DTCG](https://www.w3.org/community/design-tokens/2025/10/28/design-tokens-specification-reaches-first-stable-version/), [Design Tokens TR 2025.10](https://www.designtokens.org/tr/2025.10/)
- Style Dictionary : support « first-class » du format DTCG depuis la v4 ; la documentation indique que le format **2025.10 n'est pas encore entièrement supporté**, le support complet étant « en cours pour la v5 » — [Style Dictionary – DTCG](https://styledictionary.com/info/dtcg/). Version courante 5.6.1 (2026-10-10), Apache-2.0, `node >=22` — [npm style-dictionary](https://registry.npmjs.org/style-dictionary/latest)
- Terrazzo (outil centré DTCG) : `@terrazzo/cli` 2.7.1 (2026-08-11), MIT — [npm @terrazzo/cli](https://registry.npmjs.org/@terrazzo%2Fcli)
- Tailwind CSS 4.3.3 (2026-07-16), MIT ; plugin `@tailwindcss/vite` compatible Vite 5 à 8 — [npm tailwindcss](https://registry.npmjs.org/tailwindcss), [npm @tailwindcss/vite](https://registry.npmjs.org/@tailwindcss%2Fvite/latest). Les variables de thème sont déclarées en CSS avec `@theme` ; « All of your theme variables are turned into regular CSS variables when you compile your CSS » ; `--color-*: initial` (ou `--*: initial`) supprime le thème par défaut ; `@theme static` force l'émission de toutes les variables ; lecture en JS : `getComputedStyle(document.documentElement).getPropertyValue("--shadow-xl")` — [Tailwind theme](https://tailwindcss.com/docs/theme)
- `stylelint-declaration-strict-value` 1.12.1 (2026-08-24), MIT, compatible `stylelint >=16 <=17` : impose variables/fonctions/mots-clés autorisés pour une liste de propriétés (ex. `["/color$/", "z-index", "font-size"]`), avec `ignoreValues`, `ignoreVariables`, `ignoreFunctions` — [dépôt](https://github.com/AndyOGo/stylelint-declaration-strict-value), [npm](https://registry.npmjs.org/stylelint-declaration-strict-value/latest). Stylelint 17.16.0 (2026-10-01) — [npm stylelint](https://registry.npmjs.org/stylelint)
- Autres options (versions) : Open Props 1.7.23 (2026-01-31 ; 2.0 en bêta), UnoCSS 66.10.5, Panda CSS 2.2.0, vanilla-extract 1.21.3 — [npm open-props](https://registry.npmjs.org/open-props), [npm unocss](https://registry.npmjs.org/unocss), [npm @pandacss/dev](https://registry.npmjs.org/@pandacss%2Fdev), [npm @vanilla-extract/css](https://registry.npmjs.org/@vanilla-extract%2Fcss)

### Inferences
- **Trois niveaux de tokens** : primitifs (`color.blue.500`, `space.4`), sémantiques (`color.surface`, `color.feedback.erreur`, `font.lecture`), composants/jeu (`clavier.touche.fond`, `doigt.index-gauche.couleur`). Seuls les sémantiques sont utilisables dans les composants ; les primitifs ne servent qu'aux thèmes.
- **Partage CSS ↔ canvas** : deux voies complémentaires. (1) Build : Style Dictionary émet `tokens.css` et `tokens.ts` (valeurs résolues par thème) ; (2) Exécution : un petit service `theme.lire('--color-surface')` s'appuyant sur `getComputedStyle`, mis en cache et invalidé au changement de thème, garantit que le canvas suit les surcharges utilisateur (contraste, taille).
- **Tailwind ou non ?** Tailwind v4 est compatible avec l'approche (ses tokens *sont* des custom properties) et très bien connu des LLM, mais les classes utilitaires arbitraires (`p-[13px]`, `text-[#333]`) réintroduisent des valeurs en dur difficiles à interdire. Pour un projet où « aucune valeur en dur » est une exigence, **CSS natif scoped (Svelte) + custom properties + Stylelint strict** est plus simple à verrouiller. Si Tailwind est retenu : `--*: initial`, tokens générés dans `@theme`, et règle ESLint interdisant les valeurs arbitraires.
- **Verrouillage** : Stylelint (`declaration-strict-value` sur couleurs, tailles de police, espacements, rayons, z-index, durées) + `color-no-hex`/`color-named: never`/`declaration-property-unit-disallowed-list` ; côté TS, règle ESLint `no-restricted-syntax` contre les littéraux couleur/px dans le code de rendu canvas ; exécution en hook Claude Code `PostToolUse` et en CI.
- Écrire les tokens au format DTCG « de base » (`$value`, `$type`, alias) plutôt qu'avec les nouveautés 2025.10 (resolver/thèmes) tant que Style Dictionary ne les supporte pas entièrement ; gérer les thèmes par fichiers séparés.

### Gaps
- État exact du support DTCG 2025.10 dans Style Dictionary 5.6 (objets couleur, module resolver) non vérifié au-delà de la page de doc.
- Aucune comparaison sourcée Style Dictionary vs Terrazzo ; Panda CSS, UnoCSS, vanilla-extract et Open Props n'ont pas été analysés au-delà de leurs versions.
- Règles Stylelint natives citées en inférence non vérifiées contre Stylelint 17.

## 5. Internationalisation

### Takeaway
**Paraglide JS 2** (compilation en fonctions typées, tree-shaking) pour les chaînes d'interface ; contenus pédagogiques (listes de mots, leçons, progressions par disposition) dans des fichiers de données séparés par langue et par disposition, chargés à la demande ; traduction communautaire via **Hosted Weblate (offre Libre)**.

### Cited Findings
- Paraglide JS 2.27.0 (2026-10-09), MIT ; `vite >=5`, `typescript >=5.6` — [npm @inlang/paraglide-js](https://registry.npmjs.org/@inlang%2Fparaglide-js/latest). Le compilateur transforme les messages d'un projet inlang en fonctions ESM typées (autocomplétion des clés et paramètres, fautes de frappe = erreurs de compilation) que le bundler peut éliminer si inutilisées ; plugin Vite ; guides SvelteKit, Astro, React Router, TanStack Start ; formats de messages par plugins (format inlang, JSON, i18next, XLIFF, ICU MessageFormat 1) ; pluriels, nombres, dates, variantes (genre) ; outils : Sherlock (extension VS Code), Fink (éditeur web pour non-développeurs), CLI de traduction automatique et de vérification en CI. L'éditeur annonce « jusqu'à 70 % » de bundle en moins (exemple : 47 kB contre 205 kB pour i18next, 5 locales × 200 messages) — [paraglidejs.com](https://paraglidejs.com/)
- i18next 26.4.3 (2026-10-10), MIT ; bundle UMD min mesuré 43 kB → 13,3 kB gzip (hors ressources et plugins) — [npm i18next](https://registry.npmjs.org/i18next), [fichier mesuré](https://cdn.jsdelivr.net/npm/i18next@26.4.3/dist/umd/i18next.min.js)
- Lingui 6.9.1 (2026-10-09), MIT ; FormatJS `@formatjs/intl` 6.1.3 (2026-10-05), MIT ; typesafe-i18n 5.27.1 (dernière publication 2026-02-11) — [npm @lingui/core](https://registry.npmjs.org/@lingui%2Fcore), [npm @formatjs/intl](https://registry.npmjs.org/@formatjs%2Fintl), [npm typesafe-i18n](https://registry.npmjs.org/typesafe-i18n)
- Hosted Weblate : offre gratuite « Libre » réservée aux **projets publics**, avec les limites du plan 160k ; offres payantes à partir de 39 €/mois ; auto-hébergement gratuit — [weblate.org/hosting](https://weblate.org/en/hosting/)
- Crowdin open source : gratuit sous conditions — licence approuvée OSI, code public, pas de produit commercial lié, être chef de projet, **projet actif depuis au moins trois mois**, communauté active, section « News » à jour, versions régulières ; acceptation de contribuer les traductions à la mémoire globale de Crowdin — [Crowdin open-source request](https://crowdin.com/page/open-source-project-setup-request)

### Inferences
- Séparer strictement **trois natures de contenu** : (1) chaînes d'interface (`messages/{locale}.json`, Paraglide, traduites sur Weblate) ; (2) contenu pédagogique (`contenu/{locale}/mots.json`, `lecons/{locale}/{disposition}.json`) — non « traduisible » au sens strict : fréquences de lettres, digrammes et progression dépendent de la langue *et* de la disposition, donc rédigé par langue, validé par schéma et testé (chaque leçon ne doit contenir que des caractères atteignables avec les touches déjà apprises, vérifiable automatiquement via l'index inverse des dispositions) ; (3) audio/voix par langue.
- Locale d'interface, langue du contenu et disposition clavier sont **trois réglages indépendants** (un enfant francophone en Suisse : interface fr, contenu fr, QWERTZ CH ; un élève allophone : interface en, contenu fr, AZERTY).
- Paraglide convient au statique : la locale peut être portée par l'URL (pages prérendues par langue) ou par un réglage de profil stocké localement. Son format compilé rend impossible l'oubli d'une clé (erreur de type), un garde-fou appréciable quand des agents IA écrivent le code.
- Crowdin exige trois mois d'existence et une communauté : inaccessible au démarrage. Weblate Libre est accessible dès que le dépôt est public sous licence libre ; son modèle « fichiers dans le dépôt git » s'accorde avec un flux piloté par agents (PR automatiques de traductions).
- Utiliser `Intl.PluralRules`, `Intl.NumberFormat`, `Intl.Segmenter` (découpage en graphèmes pour compter caractères et erreurs) natifs plutôt que des bibliothèques.

### Gaps
- Stratégies de détection de locale de Paraglide (URL, cookie, localStorage, `baseLocale`) et son comportement précis avec `adapter-static` non confirmés par la page consultée.
- Tolgee (offre open source) non étudié ; conditions exactes d'approbation de Weblate Libre (licence exigée, délai) non précisées par la page lue.
- Sources de listes de mots libres par langue (Lexique, Wiktionnaire, etc.) et leurs licences : hors périmètre de cette recherche.

## 6. Persistance locale sans backend

### Takeaway
**IndexedDB** (via `idb-keyval` ou `idb`, ou Dexie si requêtes riches) comme stockage principal, `navigator.storage.persist()` demandé après une première interaction, et surtout **export/import de sauvegarde par fichier** : sous Safari, tout stockage inscriptible par script est effacé après 7 jours d'utilisation du navigateur sans interaction avec le site (hors application installée sur l'écran d'accueil). Une synchronisation ultérieure est possible gratuitement (Cloudflare Workers + D1), mais transforme le projet en responsable de traitement de données de mineurs.

### Cited Findings
- Quotas : Firefox — best-effort : min(10 % du disque, 10 GiB) par groupe ; persistant : jusqu'à 50 % du disque ; Chromium — jusqu'à 60 % du disque par origine ; Safari 17+ — ~60 % du disque par origine pour un navigateur ; Web Storage (`localStorage`) limité à 5 MiB par origine (`QuotaExceededError` au-delà) — [MDN Storage quotas and eviction criteria](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- `navigator.storage.persist()` : Firefox affiche une demande à l'utilisateur ; Safari et Chromium acceptent ou refusent **automatiquement** selon l'historique d'interaction avec le site. Éviction LRU par origine sous pression de stockage, tout-ou-rien par origine ; les origines persistantes sont épargnées — [MDN Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria)
- Safari, éviction proactive : avec la prévention du pistage intersite activée, une origine sans interaction utilisateur depuis **sept jours d'utilisation du navigateur** voit ses données créées par script supprimées — [MDN Storage quotas](https://developer.mozilla.org/en-US/docs/Web/API/Storage_API/Storage_quotas_and_eviction_criteria). Annonce d'origine (2020) : suppression de « all of a website's script-writable storage after seven days of Safari use without user interaction on the site » (IndexedDB, LocalStorage, SessionStorage, enregistrements et caches de service worker) ; les applications web ajoutées à l'écran d'accueil ont **leur propre compteur** de jours d'utilisation, et WebKit ne s'attend pas à ce que leurs données soient supprimées — [WebKit blog 2020](https://webkit.org/blog/10218/full-third-party-cookie-blocking-and-more/)
- Politique de stockage WebKit (Safari 17+) : WebKit accorde le mode persistant selon des heuristiques « comme le fait que le site soit ouvert en tant que Home Screen Web App » ; les origines persistantes ou ayant une page active sont exclues de l'éviction — [WebKit – Updates to Storage Policy](https://webkit.org/blog/14403/updates-to-storage-policy/). Un rapport de bogue signale `navigator.storage.persist()` renvoyant toujours `false` dans Safari 17 — [WebKit bug 271401](https://bugs.webkit.org/show_bug.cgi?id=271401)
- Bibliothèques : `idb-keyval` 6.3.0 (Apache-2.0) : 7 kB → **1,5 kB gzip** ; `idb` 8.0.4 (ISC) : 11 kB → 3,3 kB gzip ; Dexie 4.4.6 (Apache-2.0) : 94 kB → **30 kB gzip** — [npm idb-keyval](https://registry.npmjs.org/idb-keyval), [npm idb](https://registry.npmjs.org/idb), [npm dexie](https://registry.npmjs.org/dexie) ; fichiers mesurés : [idb-keyval](https://cdn.jsdelivr.net/npm/idb-keyval@6.3.0/dist/index.js), [idb](https://cdn.jsdelivr.net/npm/idb@8.0.4/build/index.js), [dexie](https://cdn.jsdelivr.net/npm/dexie@4.4.6/dist/dexie.min.js)
- Cloudflare D1 (plan Workers gratuit) : 5 millions de lignes lues/jour, 100 000 lignes écrites/jour, 5 Go au total ; au-delà, les requêtes échouent jusqu'à la remise à zéro quotidienne (00:00 UTC) — [Cloudflare D1 pricing](https://developers.cloudflare.com/d1/platform/pricing/). Workers gratuit : 100 000 requêtes/jour, 10 ms CPU par invocation ; KV gratuit : 1 000 écritures/jour, 100 000 lectures/jour, 1 Go — [Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)
- Supabase gratuit (sources tierces concordantes, non vérifiées sur le site officiel) : 2 projets actifs, 500 Mo de base, 50 000 utilisateurs actifs mensuels, **mise en pause après 7 jours sans activité** avec réactivation manuelle — [costbench](https://costbench.com/software/database-as-service/supabase/free-plan/), [automationatlas](https://automationatlas.io/answers/supabase-free-tier-limits-2026/)
- RGPD/mineurs (France) : seuil de 15 ans (art. 8 RGPD, art. 45 loi Informatique et Libertés) pour consentir seul à un traitement fondé sur le consentement ; en dessous, consentement conjoint du mineur et du titulaire de l'autorité parentale ; « les textes ne reconnaissent pas une “majorité numérique globale” à 15 ans ». La CNIL recommande : service adapté au public mineur, **minimisation**, information claire et adaptée, possibilité pour les parents de demander la suppression du compte — [CNIL, recommandation 1](https://www.cnil.fr/fr/recommandation-1-encadrer-la-capacite-dagir-des-mineurs-en-ligne)

### Inferences
- **Modèle** : une base IndexedDB `dactylo` avec magasins `profils`, `progression`, `sessions`, `reglages` ; chaque enregistrement porte `profilId` et une `versionSchema` (migrations testées). Les réglages légers nécessaires avant hydratation (thème, locale) peuvent être dupliqués dans `localStorage` pour éviter un flash.
- **Profils multiples sur un même appareil** (fratrie, classe, orthophoniste) : pseudonyme + avatar, **aucune donnée identifiante** (ni nom, ni e-mail, ni date de naissance) ; écran de choix de profil au lancement ; aucun mot de passe (un simple code visuel optionnel).
- **Sauvegarde** : bouton « Exporter ma progression » produisant un fichier JSON versionné (éventuellement compressé) ; import avec validation de schéma et fusion ; rappel doux d'export après N séances, surtout sur Safari non installé. Un code court ou QR n'est réaliste que pour un état compact (niveaux, étoiles), pas pour l'historique détaillé ; la File System Access API (écriture directe dans un fichier choisi) n'existe que dans Chromium.
- **Stratégie Safari/iPad** : détecter Safari non installé et expliquer l'ajout à l'écran d'accueil (compteur séparé, persistance probable) ; appeler `persist()` après un geste ; ne jamais supposer la durabilité.
- **Synchronisation ultérieure** : dès qu'un serveur stocke la progression d'un enfant, le porteur du projet devient responsable de traitement (information, base légale, consentement parental sous 15 ans, sécurité, durées de conservation, sous-traitants éventuellement hors UE). Variante à moindre risque : synchronisation « à connaissance nulle » par code de salon — blob chiffré côté client, sans compte, stocké avec une durée de vie courte (Workers + KV/D1). Supabase gratuit est fragilisé par la mise en pause ; PocketBase suppose un serveur (donc un coût ou une machine) ; Firebase implique Google et des transferts hors UE.

### Gaps
- Comportement actuel (Safari 26.x) du plafond de 7 jours et de `persist()` non vérifié sur source 2026 ; à tester sur appareil.
- Aucune source consultée sur la synchronisation chiffrée de bout en bout sans compte, ni sur PocketBase et Firebase (quotas 2026, localisation des données).
- Les limites Supabase proviennent de sites tiers ; à confirmer sur la page tarifaire officielle.
- Pas de source sur les formats d'export par QR code (capacité utile, bibliothèques).

## 7. PWA et hors-ligne

### Takeaway
Une PWA installable et entièrement hors-ligne est réalisable sans coût : manifeste + service worker précachant l'application (via le **service worker intégré de SvelteKit** ou `vite-plugin-pwa` 2 / Workbox 7). L'installation fonctionne sur Chromium (Windows, macOS, Linux, ChromeOS, Android), Safari macOS 14+ (« Ajouter au Dock ») et iOS/iPadOS 16.4+ (menu Partager, tout navigateur) ; **Firefox bureau n'installe pas les PWA**. Sur iOS, pas d'invite d'installation programmable.

### Cited Findings
- Installabilité : manifeste lié sur chaque page ; Chromium exige `name`/`short_name`, icônes 192 px et 512 px, `start_url`, `display` ; HTTPS (ou localhost) requis ; **le service worker n'est pas requis pour l'installation**. Support : Chromium bureau oui ; Safari bureau oui (Add to Dock, macOS Sonoma / Safari 17+) ; **Firefox bureau non** ; Android : Chrome et Samsung Internet installent un WebAPK, Firefox/Edge/Opera ajoutent un raccourci ; iOS ≤ 16.3 Safari seul ; iOS 16.4+ : Safari, Chrome, Edge, Firefox, Orion via le menu Partager. `beforeinstallprompt` **non supporté sur iOS** — [MDN Making PWAs installable](https://developer.mozilla.org/en-US/docs/Web/Progressive_web_apps/Guides/Making_PWAs_installable)
- iOS/iPadOS 26 : tout site ajouté à l'écran d'accueil depuis Safari s'ouvre désormais **par défaut comme une web app**, même sans manifeste (option désactivable par l'utilisateur) — [Michael Tsai, oct. 2025](https://mjtsai.com/blog/?p=49472)
- iOS : pas de Background Sync ; Web Push seulement pour les web apps installées (16.4+) ; les données d'une web app d'écran d'accueil sont isolées de celles de Safari (l'utilisateur repart d'un stockage vide après installation) — [MagicBell, guide iOS PWA (source éditeur)](https://www.magicbell.com/blog/pwa-ios-limitations-safari-support-complete-guide)
- `vite-plugin-pwa` 2.0.0 (2026-10-03), MIT ; compatible Vite 3 à 8 ; dépend de `workbox-build`/`workbox-window` ^7.4.1 ; `node >=20.19` — [npm vite-plugin-pwa](https://registry.npmjs.org/vite-plugin-pwa/latest). Génère le manifeste, le service worker (stratégies `generateSW`/`injectManifest` de Workbox) et le script d'enregistrement ; `registerType: 'autoUpdate'` ; `devOptions.enabled` pour tester en dev ; intégrations SvelteKit, Astro, Nuxt, etc. — [Vite PWA guide](https://vite-pwa-org.netlify.app/guide/). Workbox : `workbox-build` 7.4.1 (2026-05-04) — [npm workbox-build](https://registry.npmjs.org/workbox-build)
- `@vite-pwa/sveltekit` 1.1.0 ne déclare que `@sveltejs/kit ^1.3.1 || ^2.0.1` (pas Kit 3) — [npm @vite-pwa/sveltekit](https://registry.npmjs.org/@vite-pwa%2Fsveltekit/latest)
- SvelteKit embarque et enregistre automatiquement un service worker si `src/service-worker/index.ts` (ou `src/service-worker.ts`) existe ; modules fournis : `$app/service-worker`, `$app/env` (`version`), `$app/manifest` (`immutable`, `assets`, `prerendered`) ; schéma documenté : précache à l'installation dans un cache versionné, purge des anciens caches à l'activation, cache-first pour les assets de build ; bundle produit en production uniquement ; la doc renvoie vers Workbox / Vite PWA pour ceux qui les préfèrent — [SvelteKit service workers](https://svelte.dev/docs/kit/service-workers)

### Inferences
- Application 100 % statique → stratégie simple : **précache intégral** du shell, des données de dispositions et de la locale active ; mise en cache à la demande (runtime) des autres locales, des polices et des paquets audio ; mise à jour avec invite « Nouvelle version disponible » (éviter `skipWaiting` silencieux pendant une partie).
- Le service worker natif de SvelteKit (≈ 40 lignes) est suffisant et supprime une dépendance non encore compatible Kit 3 ; `vite-plugin-pwa` reste utile pour générer manifeste et icônes si l'on reste en Kit 2 ou en Vite pur.
- Prévoir une page « Installer l'application » par plateforme (Chrome/Edge : bouton via `beforeinstallprompt` ; iOS/iPadOS : pas-à-pas Partager → Sur l'écran d'accueil ; macOS Safari : Fichier → Ajouter au Dock ; Firefox bureau : utilisation en onglet + rappel d'export).
- Conséquence de l'isolation iOS : proposer l'installation **avant** la création du premier profil, ou l'export/import lors du passage Safari → web app installée.
- Le quota d'une origine étant large mais le précache coûteux en données mobiles, garder le premier chargement sous ~1 Mo compressé (hors audio) et charger les voix par paquets.

### Gaps
- Limites PWA iOS 2026 non vérifiées sur source WebKit primaire (état dans l'UE, quotas des web apps installées, comportement du clavier matériel en mode standalone).
- Notes de version et changements cassants de `vite-plugin-pwa` 2.0.0 non lus (la doc consultée affichait encore v1.2.0).
- Comportement d'installation sur ChromeOS géré (Chromebooks scolaires avec politiques d'administration) non étudié.

## 8. Audio et synthèse vocale

### Takeaway
Effets sonores via **Web Audio API en direct** (tampons décodés, lecture à la frappe), sans dépendance : Howler.js n'a plus de publication depuis septembre 2023. Pour la voix (consignes, lettres, mots dictés), `speechSynthesis` est trop inégal selon navigateur/OS pour un public dys : privilégier des **fichiers audio pré-générés** (Piper, voix française issue du jeu de données SIWIS sous CC BY 4.0) et ne garder `speechSynthesis` qu'en repli optionnel.

### Cited Findings
- Autoplay : un média avec son n'est autorisé à démarrer que s'il est muet, si l'utilisateur a interagi avec le site (« by clicking, tapping, pressing keys, etc. »), si le site est en liste blanche ou via Permissions Policy ; pour Web Audio, démarrer un nœud source hors d'un gestionnaire d'entrée utilisateur est soumis aux mêmes règles ; `navigator.getAutoplayPolicy("audiocontext")` renvoie `allowed` / `allowed-muted` / `disallowed` (non disponible partout) ; Firefox : `media.autoplay.block-webaudio` (par défaut vrai) n'autorise les contextes audio qu'après activation persistante — [MDN Autoplay guide](https://developer.mozilla.org/en-US/docs/Web/Media/Guides/Autoplay)
- Howler.js : dernière version **2.2.4 du 2023-09-19** ; dernier push du dépôt 2025-11-23 ; MIT ; 35 kB min → 9,5 kB gzip (7,7 kB pour `howler.core`) — [npm howler](https://registry.npmjs.org/howler), [goldfire/howler.js](https://github.com/goldfire/howler.js), [fichier mesuré](https://cdn.jsdelivr.net/npm/howler@2.2.4/dist/howler.min.js)
- `speechSynthesis` selon les plateformes (guide Readium, données 2024) : **Chrome bureau** — 19 voix Google de bonne qualité sur 15 langues mais **uniquement en ligne**, bogue au-delà de ~14 s d'énoncé, pas d'événements `boundary` ; **Edge bureau** — 250+ voix « naturelles » en ligne ; **Edge Android** — liste de voix vide (API inutilisable) ; **Firefox bureau** — aucune voix propre (voix du système) ; **Safari/macOS/iOS** — les meilleures voix (Siri) ne sont pas exposées, les voix téléchargées n'apparaissent pas toujours, toutes les voix se déclarent `default` ; **Android** — bonnes voix mais à télécharger dans les réglages, Chrome liste des langues sans pack installé et **retombe sur une voix anglaise** si le pack manque ; **ChromeOS** — packs souvent désinstallés après mise à jour, voix eSpeak « à éviter » (très basse qualité) — [Readium – SpeechSynthesis in browsers and OSes](https://readium.org/speech/docs/WebSpeech.html)
- `getVoices()` : synchrone dans Firefox et Safari bureau, tableau vide au premier appel dans Chrome (attendre `voiceschanged`) — [Flavio Copes, Speech Synthesis API](https://flaviocopes.com/speech-synthesis-api/)
- Piper : le dépôt d'origine `rhasspy/piper` (MIT) est **archivé** (dernière release 2023.11.14-2) ; le développement continue dans `OHF-Voice/piper1-gpl` sous **GPL-3.0** (v1.8.0, 2026-09-04) — [rhasspy/piper](https://github.com/rhasspy/piper), [OHF-Voice/piper1-gpl](https://github.com/OHF-Voice/piper1-gpl)
- Voix françaises Piper disponibles : `fr_FR` siwis (low, medium), tom, upmc (medium) — [rhasspy/piper-voices fr_FR](https://huggingface.co/rhasspy/piper-voices/tree/4d68f18217d5c6a4b2418c8c46222d6fcd698acb/fr/fr_FR). La voix siwis est entraînée sur le corpus SIWIS de l'Université d'Édimbourg, sous **CC-BY 4.0** — [MODEL_CARD siwis medium](https://huggingface.co/rhasspy/piper-voices/raw/main/fr/fr_FR/siwis/medium/MODEL_CARD)

### Inferences
- **Effets à la frappe** : un seul `AudioContext` créé puis `resume()` au premier geste (dans un jeu de frappe, la première touche pressée est un geste valide) ; sons courts décodés une fois (`decodeAudioData`) et joués par `AudioBufferSourceNode` neufs (polyphonie, pas de latence de décodage) ; `latencyHint: 'interactive'`. L'élément `<audio>` est à éviter pour le retour de frappe (latence et limites de lecture simultanée sur mobile).
- **Accessibilité sensorielle (TDAH/dys)** : volumes séparés (effets, voix, musique), mode silencieux complet, retour visuel toujours redondant avec le son, option « son d'erreur doux/aucun ».
- **Voix** : pour dicter lettres, syllabes et mots de façon identique partout, générer hors-ligne (script de build, pas en CI à chaque commit) des fichiers par locale avec Piper, les regrouper en paquets par leçon, les précacher à la demande. La licence GPL-3.0 du moteur Piper concerne le logiciel, pas les fichiers audio produits ; le modèle siwis dérive d'un corpus CC BY 4.0 → créditer le corpus dans les mentions (inférence juridique à faire valider). Vérifier la carte de modèle de chaque voix retenue (tom, upmc).
- `speechSynthesis` reste intéressant en repli pour les contenus dynamiques (mots personnalisés par un parent), avec filtrage des voix par préfixe de langue, détection de voix `localService`, et avertissement si aucune voix française n'est disponible.

### Gaps
- Aucune source consultée sur la latence audio réelle (`baseLatency`/`outputLatency`, casques Bluetooth, Android) ni sur les formats à privilégier (Opus/WebM vs AAC/MP3 selon Safari).
- Aucune source spécifique sur la qualité des **voix françaises** par plateforme, ni sur Linux (speech-dispatcher) ; licences des voix Piper `tom` et `upmc` non vérifiées.
- Alternatives à Howler (Tone.js 15.1.22, avril 2025) non analysées ; TTS neuronaux exécutés dans le navigateur (WASM) non étudiés.
- Statut juridique précis des sorties audio d'un modèle entraîné sur un corpus CC BY : non sourcé.

## 9. Hébergement gratuit et mesure d'audience

### Takeaway
**GitHub Pages depuis un dépôt public** couvre le besoin (1 Go, 100 Go/mois, domaine personnalisé, déploiement par Actions gratuit en dépôt public). Sur l'offre GitHub Free, Pages n'est disponible **que pour les dépôts publics** : un dépôt privé exige une offre payante. **Cloudflare Pages** est l'alternative la plus généreuse (pas de plafond de bande passante annoncé, prévisualisations illimitées). Pour l'audience : aucune mesure par défaut, ou un compteur sans cookie (GoatCounter, Cloudflare Web Analytics).

### Cited Findings
- GitHub Pages : site publié ≤ 1 Go ; dépôt source recommandé ≤ 1 Go ; **limite souple de 100 Go de bande passante par mois** ; limite souple de 10 builds/heure (non applicable aux déploiements par workflow GitHub Actions personnalisé) ; délai d'expiration des déploiements 10 min ; usage interdit comme hébergement gratuit d'une activité commerciale ou d'un SaaS — [GitHub Pages limits](https://docs.github.com/en/pages/getting-started-with-github-pages/github-pages-limits)
- GitHub Free (comptes personnels et organisations) : « GitHub Pages in public repositories » ; Pages en dépôt privé figure dans les fonctionnalités de GitHub Pro et Team ; la publication d'un site Pages *à accès privé* requiert une organisation sous Enterprise Cloud — [About GitHub's plans](https://docs.github.com/en/get-started/learning-about-github/githubs-plans)
- GitHub Actions : gratuit pour les **dépôts publics** sur runners standards hébergés et pour les runners auto-hébergés ; dépôts privés : 2 000 min/mois et 500 Mo d'artefacts (Free), 3 000 min (Pro, Team) ; cache 10 Go par dépôt ; tarifs indicatifs : Linux 2 cœurs 0,006 $/min, Windows 2 cœurs 0,010 $/min, macOS 0,062 $/min — [GitHub Actions billing](https://docs.github.com/en/billing/concepts/product-billing/github-actions). Le projet de facturer 0,002 $/min les runners auto-hébergés en dépôt privé (annoncé déc. 2025 pour mars 2026) a été reporté — [The Register](https://www.theregister.com/2025/12/17/github_charge_dev_own_hardware/)
- Cloudflare Pages (gratuit) : 500 builds/mois, 1 build simultané, délai de build 20 min, **prévisualisations actives illimitées**, 100 domaines personnalisés par projet, 20 000 fichiers par site, 25 MiB par fichier, 100 projets ; aucune limite de bande passante ou de requêtes statiques n'est indiquée sur la page — [Cloudflare Pages limits](https://developers.cloudflare.com/pages/platform/limits/). Sur Workers, les requêtes vers les ressources statiques sont gratuites et illimitées — [Cloudflare Workers pricing](https://developers.cloudflare.com/workers/platform/pricing/)
- Netlify (2026) : modèle à **crédits** (300 crédits/mois pour les nouveaux comptes gratuits), plafond dur — sites mis en pause une fois les crédits épuisés ; les sources tierces divergent sur le coût par Go (10 à 20 crédits) ; un fil de la communauté signale en juillet 2026 des blocages de déploiement erronés sur l'offre gratuite — [netli.fyi](https://netli.fyi/blog/netlify-free-plan-limits-2026), [Netlify community](https://answers.netlify.com/t/free-plan-run-out-of-credits-banner-but-29-9-30-credits-remaining-deploys-blocked/165263)
- Vercel Hobby : usage personnel **non commercial**, 100 Go de bande passante/mois sans achat possible de dépassement — [deploywise (tiers)](https://deploywise.dev/blog/vercel-free-tier-limits-2026)
- Codeberg Pages : nouveau service fondé sur **git-pages depuis décembre 2025** (déploiement par envoi direct/webhook, domaine personnalisé autorisé par enregistrement TXT) ; l'ancien Pages Server v2 est fermé aux nouveaux utilisateurs pour cause d'abus ; la documentation est contradictoire sur le support des domaines personnalisés pendant la transition — [Codeberg – Migrating from Pages v2](https://docs.codeberg.org/codeberg-pages/migrating-from-pages-v2/), [Codeberg Pages](https://docs.codeberg.org/codeberg-pages/)
- Cloudflare Web Analytics : gratuit ; « does not use any client-side state, such as cookies or localStorage » ; pas d'empreinte par IP/User-Agent ; fonctionne par balise JavaScript sans que le site soit proxifié par Cloudflare — [Cloudflare Web Analytics](https://www.cloudflare.com/web-analytics/)
- GoatCounter : hébergement gratuit pour usage non commercial jusqu'à ~100 000 pages vues/mois, code source ouvert auto-hébergeable (sources tierces) — [agentdeals (tiers)](https://agentdeals.dev/vendor/goatcounter), [Gigazine](https://gigazine.net/gsc_news/en/20200628-goatcounter)

### Inferences
- Un projet libre a vocation à être en dépôt public : GitHub Pages et les minutes Actions sont alors gratuits sans plafond pratique. Si une phase initiale en dépôt privé est souhaitée, déployer sur **Cloudflare Pages** (qui se connecte à un dépôt privé) plutôt que payer GitHub Pro.
- Prévisualisation par PR : native et illimitée sur Cloudflare Pages ; sur GitHub Pages il faut la bricoler (sous-dossiers par PR). Pour un développement piloté par agents, les prévisualisations sont moins critiques (vérification locale via Playwright) mais utiles pour tester sur de vrais appareils (iPad, Chromebook).
- RGPD : GitHub (Microsoft) et Cloudflare sont des sociétés américaines qui voient passer les adresses IP des visiteurs ; à mentionner dans la page « confidentialité ». Aucune donnée de progression ne quitte l'appareil dans l'architecture retenue. Codeberg (association allemande) est l'option européenne mais son service Pages est en transition : à utiliser comme miroir plutôt que comme hébergement principal en 2026.
- Mesure d'audience : pour un public d'enfants, **ne rien mesurer** est le choix le plus sûr et le plus simple ; si des chiffres sont nécessaires (demandes de soutien, priorisation), un compteur sans cookie auto-déclaré dans la politique de confidentialité, sans événement lié à un profil.
- Garder le build indépendant de l'hébergeur (sortie statique `build/` + `BASE_PATH` configurable) pour pouvoir migrer en une heure ; domaine personnalisé facultatif (seul coût potentiel du projet).

### Gaps
- Framagit Pages (GitLab de Framasoft), Umami et Plausible CE auto-hébergés : non étudiés (un auto-hébergement suppose de toute façon un serveur, donc un coût ou une machine personnelle).
- Chiffres GoatCounter et Vercel issus de sources tierces ; conditions officielles à relire.
- Localisation précise des données/journaux chez GitHub Pages et Cloudflare (régions UE, durées de conservation) non sourcée.
- Fiabilité et limites chiffrées du nouveau Codeberg Pages non publiées.

- **E2E Playwright** (3 moteurs) : parcours critiques (création de profil, leçon complète en QWERTY US simulé, export/import, hors-ligne via `context.setOffline`, changement de thème/langue), audit axe sur chaque écran, captures visuelles par thème. WebKit de Playwright n'est pas Safari iOS : compléter par une liste de tests manuels sur iPad et Chromebook avant chaque version.
- **Lint** : ESLint 10 reste nécessaire pour Svelte (eslint-plugin-svelte compatible ESLint 10) ; Biome 2 est plus rapide mais son support Svelte en 2026 n'a pas été vérifié ; Oxlint peut servir de pré-passe rapide. Prettier 3 + `prettier-plugin-svelte` pour le format. Stylelint 17 pour les règles « pas de valeur en dur » (question 4).
- **Hooks git** : lefthook (binaire Go, multiplateforme, activement publié) plutôt que husky (dernière publication novembre 2024) ; pré-commit = format + lint sur fichiers modifiés ; pré-push = typecheck + tests unitaires. Les mêmes commandes sont appelées par les hooks Claude Code et par la CI (une seule source de vérité : scripts `package.json`).
- **Versionnement** : Conventional Commits + commitlint ; pour une application (non une bibliothèque), release-please (PR de version et changelog automatiques) est plus naturel que Changesets.
- **CI** : jobs séparés `lint`, `typecheck`, `unit`, `e2e` (matrice 3 navigateurs sur Linux), `build` + déploiement Pages ; Lighthouse CI en job non bloquant (outil peu maintenu).

### Gaps
- Statut « stable » du mode navigateur de Vitest 5 et API exacte des tests visuels (`toMatchScreenshot`) non confirmés par la page lue.
- Support actuel de Svelte par Biome 2.5 et par Oxlint 1.x non vérifié ; nouveautés d'ESLint 10 non lues.
- release-please : version et état de maintenance non relevés (quota API GitHub atteint).
- Possibilité d'injecter des événements clavier arbitraires (`key`/`code` non-US, `Dead`) via CDP dans Chromium : connue de l'auteur mais non sourcée ici ; sans équivalent documenté pour Firefox/WebKit.

Données de dispositions et géométries : **CC0-1.0** (faits peu protégeables, réutilisation maximale par d'autres projets), en conservant les notices Unicode/MIT des sources.

## 12. Développement piloté par agents IA (Claude Code)

### Takeaway
La documentation officielle converge sur une contrainte unique — **le contexte se remplit vite et la qualité se dégrade avec lui** — et sur quatre leviers : donner à Claude un moyen de **vérifier** son travail (tests, build, captures), garder `CLAUDE.md` **court (< 200 lignes)** en déportant le reste vers des règles par chemin, des skills et des hooks, **isoler** recherches et tâches verbeuses dans des sous-agents/worktrees, et **réinitialiser** le contexte entre tâches (`/clear`). Pour une personne seule, la structure du dépôt (paquets petits, contrats typés, tests rapides) est le principal multiplicateur.

### Cited Findings

**Mémoire et instructions**
- Deux mécanismes chargés à chaque session : fichiers `CLAUDE.md` (écrits par l'humain) et *auto memory* (notes écrites par Claude, par dépôt, partagées entre worktrees, **200 premières lignes ou 25 Ko** chargés). Ce sont du contexte, pas une configuration imposée : pour bloquer une action, utiliser un hook `PreToolUse` — [Claude Code – memory](https://code.claude.com/docs/en/memory)
- Emplacements : `./CLAUDE.md` ou `./.claude/CLAUDE.md` (projet, versionné), `./CLAUDE.local.md` (personnel, à mettre dans `.gitignore`), `~/.claude/CLAUDE.md` (utilisateur). Les fichiers des répertoires parents sont chargés au lancement ; **ceux des sous-répertoires sont chargés à la demande** quand Claude y lit des fichiers ; tous sont concaténés (pas de surcharge) — [memory](https://code.claude.com/docs/en/memory)
- Taille : « target under 200 lines per CLAUDE.md file. Longer files consume more context and reduce adherence ». Les imports `@chemin` (relatifs au fichier importeur, profondeur maximale quatre sauts) organisent mais **ne réduisent pas** le coût en contexte, car chargés au lancement. Les commentaires HTML de bloc sont retirés avant injection (utile pour des notes aux humains) — [memory](https://code.claude.com/docs/en/memory)
- `.claude/rules/*.md` : un sujet par fichier, découverte récursive ; un frontmatter `paths:` limite le chargement aux moments où Claude travaille sur des fichiers correspondants — [memory](https://code.claude.com/docs/en/memory)
- `AGENTS.md` est lu nativement (Claude Code ≥ 2.1.277) s'il n'existe aucun `CLAUDE.md` ; sinon l'importer depuis `CLAUDE.md` — [memory](https://code.claude.com/docs/en/memory)
- Contenu recommandé de `CLAUDE.md` : commandes que Claude ne peut deviner, règles de style qui diffèrent des défauts, instructions de test, conventions de dépôt, décisions d'architecture propres au projet, pièges. À exclure : ce qui se déduit du code, conventions standard, documentation d'API détaillée, informations changeantes, descriptions fichier par fichier. Test : « Would removing this cause Claude to make mistakes? ». `/init` génère un point de départ ; `/doctor` propose des coupes ; n'accentuer (« IMPORTANT ») qu'une ligne à la fois — [best practices](https://code.claude.com/docs/en/best-practices)

**Choisir le bon mécanisme**
- Coût en contexte : `CLAUDE.md` = contenu complet à chaque requête ; skills = descriptions au démarrage, contenu complet à l'usage (rien du tout si `disable-model-invocation: true`) ; serveurs MCP = noms d'outils, schémas différés ; sous-agents = contexte isolé ; hooks = zéro sauf sortie renvoyée — [features overview](https://code.claude.com/docs/en/features-overview)
- Déclencheurs d'ajout : erreur de convention répétée deux fois → `CLAUDE.md` ; même procédure collée trois fois → skill ; tâche annexe qui inonde la conversation → sous-agent ; action devant se produire à chaque fois → hook. « Put guardrails in hooks » : une consigne dans `CLAUDE.md` est une demande, un hook `PreToolUse` est une garantie — [features overview](https://code.claude.com/docs/en/features-overview)
- Skills : `.claude/skills/<nom>/SKILL.md` (les anciennes commandes `.claude/commands/*.md` ont été fusionnées dans les skills et continuent de fonctionner) ; frontmatter `name`, `description`, `disable-model-invocation`, `allowed-tools`, `context: fork`, `agent`, `model`/`effort`, `paths`, `argument-hint` ; `$ARGUMENTS` ; injection dynamique `` !`commande` `` ; description tronquée à 1 536 caractères ; garder `SKILL.md` **sous 500 lignes** avec fichiers annexes chargés au besoin — [skills](https://code.claude.com/docs/en/skills)
- Hooks : configurés dans `.claude/settings.json` (navigateur `/hooks`) ; événements dont `PreToolUse`, `PostToolUse`, `Notification`, `SessionStart`, `UserPromptSubmit`, `Stop` ; exemples documentés : formatage automatique après `Edit|Write`, blocage d'écriture sur fichiers protégés, **réinjection de contexte après compaction** (`SessionStart` avec matcher `compact`), notification de bureau (variante PowerShell fournie pour Windows) ; hooks à base de prompt ou d'agent pour les décisions demandant du jugement — [hooks guide](https://code.claude.com/docs/en/hooks-guide)

**Vérification, planification, contexte**
- « Give Claude a way to verify its work » : tests, code de sortie d'un build, linter, capture d'écran comparée ; gradation : dans le prompt, condition `/goal`, hook `Stop` déterministe, sous-agent de vérification ; exiger des preuves (sortie de test) plutôt qu'une affirmation — [best practices](https://code.claude.com/docs/en/best-practices)
- Flux en quatre temps : explorer (mode plan, `Shift+Tab` ou `--permission-mode plan`) → planifier (`Ctrl+G` pour éditer le plan) → implémenter → committer. Le mode plan est superflu si le diff tient en une phrase. Pour une grosse fonctionnalité : se faire interviewer par Claude (`AskUserQuestion`), produire `SPEC.md`, puis **nouvelle session** pour l'exécution — [best practices](https://code.claude.com/docs/en/best-practices)
- Gestion du contexte : `/clear` entre tâches sans rapport ; après deux corrections infructueuses, `/clear` et meilleur prompt ; `/compact <instructions>` ; résumé partiel via `/rewind` ; `/btw` pour une question qui ne doit pas entrer dans l'historique ; consigne de compaction dans `CLAUDE.md` ; points de contrôle (`Esc Esc`) — qui ne remplacent pas git — [best practices](https://code.claude.com/docs/en/best-practices)
- Échecs types : session fourre-tout, corrections en boucle, `CLAUDE.md` sur-spécifié, écart confiance/vérification, exploration infinie — [best practices](https://code.claude.com/docs/en/best-practices)

**Sous-agents, worktrees, parallélisme**
- Sous-agents intégrés : Explore (lecture seule), Plan, general-purpose ; personnalisés dans `.claude/agents/*.md` avec frontmatter `name`, `description`, `tools`, `model` (`sonnet`/`opus`/`haiku`/`fable`/`inherit`), `isolation: worktree`, `memory` (`user`/`project`/`local`), `skills`, `maxTurns`, `effort`, `background` ; contexte neuf à chaque lancement ; imbrication possible jusqu'à trois niveaux ; 20 sous-agents simultanés par défaut ; leurs requêtes comptent dans les quotas — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Les utiliser quand la tâche produit une sortie verbeuse, doit être restreinte en outils, ou est autonome ; rester dans la conversation principale pour l'itératif, les phases partageant beaucoup de contexte, les petits changements — [sub-agents](https://code.claude.com/docs/en/sub-agents)
- Worktrees : `claude --worktree <nom>` crée `.claude/worktrees/<nom>/` sur la branche `worktree-<nom>` (ajouter `.claude/worktrees/` au `.gitignore`) ; chaque worktree est un checkout neuf — **dépendances à réinstaller** ; `.worktreeinclude` copie les fichiers ignorés par git (`.env`) ; base par défaut = branche par défaut du dépôt distant (`worktree.baseRef: "head"` pour partir du travail local) ; nettoyage proposé à la sortie ; Claude Code bloque les éditions visant le checkout principal depuis un worktree ; précautions Windows documentées (liens/jonctions) — [worktrees](https://code.claude.com/docs/en/worktrees)
- Motifs : Writer/Reviewer (une session écrit, une autre relit en contexte neuf), tests écrits par une session et code par une autre, revue contradictoire par sous-agent avant de clore (en limitant le relecteur aux écarts de correction/exigences pour éviter la sur-ingénierie), `/code-review`, `/batch` (5 à 30 sous-agents en worktrees), mode non interactif `claude -p` pour CI et scripts — [best practices](https://code.claude.com/docs/en/best-practices)
- Les *agent teams* sont expérimentales, désactivées par défaut, et consomment environ **7× plus de tokens** qu'une session standard quand les coéquipiers tournent en mode plan — [costs](https://code.claude.com/docs/en/costs)

**Coûts et modèles**
- Coût moyen constaté en entreprise : ~13 $ par développeur et par jour actif, 150-250 $/mois, moins de 30 $/jour pour 90 % des utilisateurs — [costs](https://code.claude.com/docs/en/costs)
- Réduction de consommation : `/clear` entre tâches (« Stale context wastes tokens on every subsequent message ») ; Sonnet pour l'essentiel, Opus pour l'architecture, `model: haiku` pour les sous-agents simples ; préférer les CLI (`gh`) aux serveurs MCP ; plugin d'intelligence de code (LSP) pour éviter des lectures de fichiers ; hooks de prétraitement (ne renvoyer que les tests en échec) ; déplacer les procédures de `CLAUDE.md` vers des skills ; baisser l'effort de réflexion (`/effort`) sur les tâches simples ; déléguer les opérations verbeuses à des sous-agents ; prompts précis ; mode plan avant les tâches complexes — [costs](https://code.claude.com/docs/en/costs)
- Cache de prompts : automatique ; durée de vie d'une heure en abonnement, cinq minutes sur les crédits d'usage ou par clé API ; le premier message après une pause plus longue retraite tout le contexte ; `/compact` est lui-même une grosse requête alors que `/clear` ne coûte rien ; `/usage` affiche la part de tokens servis par le cache — [costs](https://code.claude.com/docs/en/costs)
- Modèles (octobre 2026) : alias `opus` → Opus 5.5, `sonnet` → Sonnet 5.5, `haiku` → Haiku 5.5 (API Anthropic) ; `fable` → Fable 5.1 pour les tâches les plus dures et longues ; `opusplan` = Opus en mode plan puis Sonnet à l'exécution ; modèle par défaut des offres Pro/Max/Team/API : Opus 5.5 ; niveaux d'effort `low` à `max` (défaut `medium` sur les modèles 5.5) — [model config](https://code.claude.com/docs/en/model-config)

### Inferences
- **Organisation proposée du dépôt pour ce projet** :
  - `CLAUDE.md` racine (≤ 100-150 lignes) : commandes (`pnpm dev/test/lint/typecheck/e2e`), carte des paquets, règles non négociables (« aucune valeur de style en dur : tokens uniquement », « toute chaîne visible passe par l'i18n », « le moteur de frappe ne dépend pas du DOM », « ne jamais juger une frappe sur `code` »), définition de « terminé » (tests + lint + typecheck verts, preuve jointe), consigne de compaction, pointeurs vers `docs/`.

- **Choix de modèle par tâche** : `opusplan` ou Opus pour la conception (moteur de frappe, modèle de données, architecture) ; Sonnet pour l'implémentation courante ; Haiku pour les sous-agents de recherche, de génération de contenu répétitif et d'exécution de tests ; Fable réservé aux chantiers longs et difficiles.

### Gaps
- Les arbitrages SvelteKit 2 vs 3, AGPL vs GPL et pnpm vs npm reposent sur des inférences et sur l'état de l'écosystème à dix jours de la sortie de Kit 3 ; à réévaluer au démarrage effectif.
- Aucune mesure de performance réelle (DOM animé sur Chromebook d'entrée de gamme ou iPad ancien) n'étaye le choix « DOM d'abord » : un prototype de mini-jeu chargé est à mesurer tôt.
- Les points listés en « Gaps » des sections 1, 6, 7 et 8 (comportements clavier réels, persistance Safari actuelle, PWA iOS, voix françaises) conditionnent la stack et ne peuvent être levés que par des essais sur appareils.
